### Задание 1

Кейс

Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.

Необходимо описать, какие варианты резервного копирования подходят в случаях:

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

Полное резервное копирование (Full Backup) + дифференциальное (Differential).
Ежедневный полный бэкап (ночью). При сбое — восстановление с последнего полного бэкапа.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

Полный бэкап + инкрементные (Incremental) или журналы транзакций (WAL / Binary Logs).
Полный бэкап (раз в сутки) + логи изменений (каждые 5–15 мин). Откат к точке во времени (PITR — Point-In-Time Recovery).

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

Репликация (Master‑Slave / Master‑Master) + автоматический failover.
Активный мастер + горячий slave (синхронная/асинхронная репликация). При падении мастер‑базы — автоматическое переключение на slave (инструменты: Patroni, MHA, Orchestrator, ProxySQL). Время переключения — секунды.

### Задание 2

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

Для создания логической резервной копии базы данных используется утилита pg_dump .

*    В текстовый SQL-файл (Plain SQL): Самый простой формат, подходит для миграций, но восстановление может быть медленным.
```bash
    pg_dump -U postgres -d mydb > mydb_backup.sql
```
*    В кастомный архив (Custom): Самый гибкий формат (-Fc). Сжат по умолчанию, позволяет использовать pg_restore для выборочного восстановления.
```bash
    pg_dump -U postgres -d mydb -Fc -f mydb_backup.dump
```
2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

Способ восстановления зависит от формата файла резервной копии.

*    Восстановление из SQL-файла (Plain): выполняется через утилиту psql.
```bash
    psql -U postgres -d mydb < mydb_backup.sql
```
*    Восстановление из архивного формата (-Fc/-Fd): выполняется через pg_restore. Ключ -C автоматически создает базу перед восстановлением.
```bash
    pg_restore -U postgres -d postgres -C mydb_backup.dump
```

### Задание 3

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.

Команда для инкрементного бэкапа зависит от используемого инструмента.

*    С помощью mysqlbackup (MySQL Enterprise Backup): Этот инструмент создаёт инкрементные копии, копируя изменения, произошедшие с последнего бэкапа (на основе LSN — Log Sequence Number). Пример команды для создания инкрементной копии в каталог:
```bash

    mysqlbackup --defaults-file=/etc/my.cnf \
      --incremental \
      --incremental-base=dir:/path/to/full_backup \
      --incremental-backup-dir=/path/to/inc_backup \
      backup
```
    **'--incremental'**: указывает на создание инкрементной копии.
    **'--incremental-base=dir:...'**: задаёт каталог с предыдущим (полным или инкрементным) бэкапом, относительно которого будут взяты изменения.

*    С помощью mysqlbinlog: Этот метод использует бинарные логи сервера. После восстановления из полного бэкапа, можно применить изменения из бинарных логов, чтобы восстановить данные до нужного момента времени (Point-in-Time Recovery)

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

Использование реплики дает значительные преимущества по сравнению с традиционным резервным копированием.
|Преимущество|	Описание|
|:-----------|:---------|
|Снижение нагрузки на Master|	Резервное копирование можно выполнять на реплике (Slave), не создавая дополнительную нагрузку на основной сервер (Master).|
|Мгновенное восстановление (Failover)|	В отличие от восстановления из бэкапа (которое может занять часы), при сбое Master-сервера можно переключиться на реплику за секунды, обеспечивая высокую доступность.|
|Консистентные снэпшоты|	Для создания резервной копии реплику можно временно остановить или заблокировать. Это позволяет сделать идеальный снэпшот "живых" данных, не прерывая работу основного сервера.|

Репликация не защищает от логических ошибок (например, случайного удаления данных оператором DELETE), так как эта команда также будет выполнена на реплике. Поэтому репликация должна дополнять, а не заменять обычные резервные копии.
